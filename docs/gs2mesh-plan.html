3DGS 转单物体 Mesh：生产方案

目标是把原场景高斯、SLAM mesh 和分割后的物体高斯，稳定转换成完整、水密、尺度真实的单物体 mesh，供机器人仿真使用。当前最大的阻塞是遮挡洞。核心思路是观测到的区域信观测，没观测到的区域按物体结构补全：由 gpt-6-astra 理解物体结构并写 Blender 建模脚本，算法负责拟合和融合，最后由质检门禁和 agent 修复回路保证产出质量。

几何主路线接触面直接封口，对称物体镜像补全，其余由 GPT 写参数化建模代码生成完整形状，再拟合到观测几何上。
Agent 的定位流水线是确定性的。Agent 通过 GPT API 做诊断、结构理解和建模代码生成；最终是否通过由指标判定。
最紧急的事查清内部高斯训练代码是否基于 Inria 官方代码；确认 gpt-6-astra 已在公司账号开通及其速率配额。

01现状与已确认信息

项目现状对方案的影响
原始照片没有，用高斯渲染图代替纹理上限偏低，可以接受。也没有训练相机位姿，所以要用虚拟相机渲染，并靠高斯覆盖度估计哪些区域被观测过（见第 04 节）。
SLAM mesh与高斯同坐标系；RGB-D，可能带激光；精度不稳定只用作尺度基准、支撑面和墙面检测、粗形状约束，不当最终几何。传感器类型暂时不用确定，见下方说明。
高斯格式原版 3DGS，内部训练，代码来源待确认需排查 许可证风险，见第 11 节。
主要问题遮挡洞修复类算法补不出来，必须引入结构先验，这是本方案的重点。
模型接入只通过外部 GPT API（如 gpt-6-astra），内部不部署任何模型不使用 3D 生成模型。形状补全改为"封口 + 对称 + GPT 写参数化建模代码"。GPU 只用于高斯渲染和深度融合这类计算。
主力工具团队主力使用 BlenderBlender 定为建模、修复、UV、烘焙、导出和 mesh 渲染的主力工具，以无界面脚本模式运行。manifold3d 只用于需要反复快速计算的参数拟合。
后续需求PBR、碰撞体、物理属性以后要现在只预留数据结构，但尺度、朝向、来源标记、UV 必须现在做对（见第 10 节）。
类别杯子、柜子、桌子、椅子、沙发、花盆等，种类多按几何特征分路线处理，不按单个类别写规则（见第 05 节）。

SLAM 传感器是 RGB-D 还是激光，影响大吗？

在本方案里影响不大，可以先不定。SLAM mesh 不直接进入最终几何，只承担三件事：

  • 米制尺度。两种传感器都是米制，都能用。
  • 支撑面和墙面检测。地面、桌面、墙面都是大平面，RGB-D 在这方面也足够可靠。接触面封口直接依赖这一步。
  • 粗形状约束。这里精度差异才明显。RGB-D 在深色、反光、细长物体上噪声大，激光在大平面和距离上更准。

做法是不预设信任度，而是按物体自动算一个一致性分数：把 SLAM mesh 和高斯渲染深度做比对，吻合的区域给 SLAM 高权重，冲突的区域降权。传感器类型和扫描质量的差异会自动反映在权重里。

02系统架构

按资源类型分层。编排层负责"任务走到哪一步"，执行层按 CPU、GPU 计算、Blender 分池，各自独立扩缩容。所有大模型调用统一经过模型网关，再到外部 GPT API。早期不拆微服务，一个编排层加几个 worker 池就够了。

工程要点

  • 编排用 Temporal：每个阶段写成幂等的 activity，中间产物落对象存储，失败只重跑当前阶段。
  • 按资源分池：CPU 池、GPU 计算池、Blender 池分开扩容，哪个池排队长就加哪个。
  • Blender 池负责所有 mesh 操作：建模、修复、减面、UV、烘焙、导出、质检用的 mesh 渲染都在这里完成，以无界面脚本模式运行（blender -b --python）。GPT 写的建模脚本也在这里执行，所以 Blender 池同时就是沙箱，具体隔离措施见第 09 节。
  • 数据本地化：一个场景的高斯可能有几百 MB 到几 GB。同一个物体的连续几个阶段尽量固定在同一台机器上执行，节点本地缓存已下载的数据，阶段之间只传裁剪后的物体数据，不传整个场景。
  • 全链路可追溯：每个物体都能回答"用了哪个模型版本、哪段建模代码、哪组参数、花了多少 token、为什么通过或没通过"。

模型网关：所有 GPT 调用的统一出口

全部依赖外部 API 时，高并发下最先卡住的往往是 API 的速率限制，而不是我们自己的算力。所以模型网关要做好这几件事：

  • 限流与排队：按账号配额控制并发，超出的请求排队，不直接报错。
  • 多通道：gpt-6-astra 在 OpenAI、Azure、AWS Bedrock 上都能调用。网关同时接两到三个通道，一个限流或故障时自动切换到另一个。
  • 重试、熔断与降级：超时或限流时自动退避重试；错误率过高时熔断，暂停调用，避免把预算浪费在失败请求上；简单任务（比如数实例个数）可以降级到同系列更便宜的型号。
  • 缓存：同样的输入不重复调用；系统提示词和工具定义利用 API 的提示缓存，降低输入成本。
  • 成本记账：按场景、物体、阶段统计 token 和费用，作为排期与报价的依据。
  • 可替换：业务代码只调用网关，不直接调用 OpenAI SDK。以后换模型或换供应商，只改网关。

03单物体流水线

六个阶段依次执行，每个阶段后面都有门禁。几何门禁不通过，就不进入纹理阶段。几何还不对就去烘焙纹理，后面怎么修都是错位的。

04遮挡洞：核心方案

遮挡洞的本质是那块表面从来没被拍到过，数据里没有任何信息。hole filling、Poisson 重建这类"修复"方法只能补出平面盖子或肿块，看起来就是半个物体。要补全，只能借助对物体结构的理解：这是一把四条腿的椅子、一个旋转对称的花盆、一个靠墙的柜子。

gpt-6-astra 在这里能做什么，不能做什么

能力情况对我们的意义
输入输出官方文档：输入是文字和图像，输出是文字不能直接输出 GLB、OBJ 等 3D 文件
空间理解OpenAI 公布的 BenchCAD 测试：看多视角渲染图、写 CAD 代码重建 3D 物体，带工具时几何重合度 95.9%正好是我们要的能力：看高斯渲染图，写出完整物体的建模代码
规则几何用户实测：规则几何、多面体做得很好桌、柜、椅、杯、花盆这类家具和器物是强项
有机形状用户实测：人、动物这类有机形状效果差，质量不如专门的 3D 生成模型软装、植物要降低预期，或走其他兜底路线
成本程序化建模通常要多轮迭代，token 消耗大要靠模板沉淀控制成本，见第 12 节

BenchCAD 是 OpenAI 自己公布的成绩，部分实测文章来自 3D 生成厂商，所以实际效果要在我们自己的测试集上验证。

补全顺序：能用简单方法就不用复杂方法

  1. 接触面封口。柜子底面贴地、背面贴墙，桌上物体的底面。这些面在现实中大多本来就是平的，沿检测到的支撑面或墙面封口就是正确结果。零 token 成本，结果最稳定。
  2. 对称补全。GPT 看多视角渲染图，判断对称类型（左右镜像、旋转对称）和大致对称轴；算法精确拟合对称轴后，把观测到的部分镜像过去，或者把轮廓旋转成完整曲面。
  3. 程序化建模。前两步补不全的情况，由 GPT 判断部件结构（比如"四条腿 + 座面 + 靠背"），写出调用我们建模工具库的参数化建模代码，在沙箱中执行，得到完整、水密的形状。

只有非接触面上的隐藏区域（沙发靠背的背面、椅背后侧、被其他物体挡住的侧面）才会造成"半个物体"的感觉，需要走第 2 或第 3 步。

关键决策：以补全模型为拓扑载体，向观测几何形变

"观测 mesh + 补全 mesh 拼接"的做法接缝处极难处理，容易出现台阶、重叠面和非流形边。本方案反过来做：

  1. 先由封口、对称或程序化建模得到一个完整、水密的候选形状；
  2. 用参数优化把它拟合到观测几何上，比如调整程序化模型的尺寸参数；
  3. 再做非刚性形变，观测区域贴到观测表面上，遮挡区域保持补全的形状。

这样拓扑始终来自完整的候选模型，天然水密、无接缝。观测数据只负责修正形状，不负责构造拓扑。

步骤拆解

步骤做法要点
A 高斯清理按不透明度、尺度异常、离群统计剔除漂浮物；用 SLAM mesh 包围盒裁剪漂浮物是后面拟合失败的主要来源
B 虚拟相机在支撑面上方的半球面上布置虚拟相机，用 SLAM mesh 做射线检测，剔除被墙或其他物体挡住的视角没有训练位姿，只能这样做。偏离训练视角太远时渲染质量会下降，所以要按清晰度和不透明度覆盖率给视角打分
C 观测几何gsplat 渲染中位深度和法线，TSDF 融合出部分表面只保留高置信区域，不追求完整
D 可见性与洞分类表面附近有高不透明度高斯且法线一致，判为已观测；靠近支撑面或墙面的缺失区判为接触洞，其余缺失区判为隐藏洞决定每块区域走哪条补全路线，是整套方案的关键
E 结构理解把 4 到 6 张多视角渲染图和观测几何的统计信息（包围盒尺寸、主平面、截面轮廓）发给 GPT，返回结构化结果：类别、部件、对称类型、关键尺寸要求 GPT 输出固定格式的 JSON，方便程序校验，不接受自由文本
F 补全按"封口 → 对称 → 程序化建模"的顺序尝试。程序化建模时，GPT 优先从模板库选模板并只给参数；没有合适模板才写新代码建模代码只能调用我们封装的建模库，保证输出是流形
G 拟合选优优化参数，让候选贴合观测。打分用单向的"观测→候选"距离，加上多视角轮廓 IoU只能用单向距离：候选比观测多出来的部分正是要补的，不能被惩罚
H 非刚性形变ARAP 或嵌入式形变图，对应点按观测置信度加权；加接触约束：底面落在支撑面上，背面贴墙形变要有正则，防止把观测噪声也拉进来
I 拓扑清理去自交、去小连通分量、按面数预算减面、水密检查程序化模型本身是水密的，这一步主要是保险

Blender 建模原语库：GPT 写的脚本只能调用这些

不让 GPT 直接写原生的 bpy 代码。bpy 依赖很多"当前状态"（选中了哪个物体、处在哪种编辑模式），代码写对了也可能因为状态不对而失败。我们在 Blender 上封装一层建模原语，GPT 只能调用这一层，比如 make_box(w, d, h, bevel)、make_leg(length, radius)、lathe(profile)。这样脚本短、出错少、结果可校验：

  • 基本体：长方体、圆柱、圆台、圆角盒、球。
  • 成形操作：旋转体（轮廓绕轴旋转）、拉伸、沿路径扫掠、放样。
  • 组合操作：布尔并、差、交（使用 Blender 4.5 起提供的 Manifold 求解器，保证结果是流形），镜像、阵列（比如四条桌腿）。
  • 造型修饰：倒角、细分曲面、平滑。沙发、抱枕这类软体主要靠这些操作，这也是选 Blender 的重要原因。
  • 从观测取数：提取截面轮廓、拟合平面和圆、测量部件尺寸。让脚本能直接引用观测数据，而不是凭图片猜尺寸。
  • 收尾规范：每个脚本结束时自动应用变换、统一单位为米、Z 轴朝上、检查流形，由原语库强制执行，不依赖 GPT 记得去做。

参数拟合不在 Blender 里做。拟合要反复"改参数、重新建模、和观测比对"，一个物体可能重复几百次。Blender 每次操作开销较大，所以拟合阶段用 manifold3d 在 CPU 池里快速计算同一套参数化模型，得到最优参数后再交给 Blender 生成最终 mesh。这要求每个模板同时有 Blender 和 manifold3d 两种实现，由同一份参数定义驱动。

值得借鉴的研究

  • Gaussian Object Carver（GOC）：从组合式高斯场景提取可分离的水密物体 mesh，把补全模块和重建解耦。借鉴它的模块划分。
  • OMEGAS：分割目标高斯后再补全。借鉴"分割和补全分两阶段"。
  • MEGA（2026 年 10 月）：用分割后的高斯渲染多视角图像作为监督信号重建物体 mesh。适合我们没有原图的情况。

这几篇都依赖 3D 生成模型做补全，我们只借鉴思路，补全模块换成"封口 + 对称 + 程序化建模"。

05按类别分流

类别很多，所以不按单个类别写规则，而是按几何特征分成几条路线。

几何特征典型类别主路线预期质量
箱体 / 平面为主柜子、桌子、床头柜、书架接触面封口 + 箱体模板参数拟合，桌腿用阵列复制高
旋转对称杯子、花盆、碗、瓶子拟合旋转轴，用观测到的轮廓旋转成完整曲面高
细长 / 镂空椅子、衣架、落地灯GPT 识别部件结构，程序化建模（杆件扫掠 + 板件），观测用于尺寸拟合较高 正是程序化建模的强项
小物件遥控器、手机、书圆角盒等模板 + 尺寸拟合，底面封口较高
软体 / 有机形状沙发、抱枕、床左右镜像补全为主，靠背背面按观测曲面平滑外推后封口中 人工复核比例较高
透明 / 强反光玻璃杯、金属锅高斯几何不可靠，主要靠 GPT 结构判断 + 模板中
细碎结构花盆里的植物单独拆成实例；几何要求降级，以外观为主低 建议与客户约定标准

路由方式：GPT 先给出类别和几何特征标签，再结合隐藏洞面积占比（第 04 节步骤 D）选择路线。只有接触洞的物体直接封口，不调用程序化建模。

06实例拆分

针对"桌子加遥控器被分割成一个整体"的情况，组合三种信号：

  • 几何信号：用 RANSAC 从 SLAM mesh 和高斯中检测支撑平面，平面以上的连通分量就是候选的独立物体。简单、稳定、可解释。
  • 颜色与密度信号：连通但颜色、密度明显不同的区域（比如紧贴桌面的桌布、书本）进一步切分。
  • GPT 校验：看多视角渲染图，回答"这里有几个独立物体、分别是什么、在图中的大致位置"。

信号一致就自动通过，不一致交给 Agent 诊断或人工复核。拆分出的每个实例带上类别标签和支撑关系（比如"遥控器放在桌面上"），后续的接触面封口要用到。原方案中的 SAM 2 / SAM 3 需要本地部署，按目前"只用外部 API"的前提先不用；如果以后允许部署，可以作为第四种信号接入。

07纹理

  1. UV 展开：在 Blender 中展开（智能 UV 投影，复杂物体可用 xatlas 作为备选），控制纹素密度一致。程序化建模的物体可以按部件分别展开，接缝更整齐。这套 UV 以后要给 PBR 复用，现在就要做好。
  2. 观测区烘焙：GPU 池从虚拟视角渲染高斯图像，Blender 池把图像按相机投影到 UV 上。每个纹素选择最佳视角，按入射角、距离、清晰度加权融合。
  3. 补全区纹理：按优先级处理。对称补全的区域，从对称的另一侧拷贝纹理；程序化建模的区域，沿用同一部件观测区的主材质（比如椅腿统一用已观测椅腿的颜色和纹理）；接触面（底面、贴墙面）用相邻区域的主色。边界处在 UV 空间羽化融合。
  4. 文字和标签：GPT 识别残缺内容。规则是宁可模糊，也不能出现错乱字符，并设单独的质检项。gpt-6-astra 支持图像生成工具，以后可以评估用它做局部重绘，但要先验证多视角一致性。
  5. 光照：高斯颜色里含有场景光照。现阶段直接使用；以后需要 PBR 时再加去光照和材质估计阶段，UV 和来源标记已经就绪。

08质检门禁与指标定义

本节是团队讨论稿指标的定义方法已经确定，具体标准和阈值需要团队和客户一起敲定。文末列出了讨论要点。

核心思路：指标就是把"人眼判断合格不合格"变成机器能自动做的检查。所以先有人的判断，再有指标，最后用人的判断去校准指标。门禁由指标判定，不由 GPT 判定。

第一步：用大白话写出"什么叫合格"

站在客户的角度想：机器人公司拿到一个 mesh 或 USD，什么情况会说"这个不能用"？

  1. 导入仿真软件就报错，或者物理仿真出问题（穿模、乱弹）。
  2. 尺寸不对，比如杯子有半米高。
  3. 形状和真实物体对不上。
  4. 看起来不完整，有洞、只有半边。
  5. 颜色、纹理和真实物体差太多。
  6. 贴图有明显的接缝、错位、乱码文字。

这份清单最好直接问客户要。客户很可能已经有验收标准，或者能说出以前拒收过什么样的数据。客户的标准是最权威的指标来源。

第二步：给每条标准找一个机器能测的信号

我们没有真实物体做对比，但手里有四种参照：原始高斯（拍到的形状和颜色可信）、SLAM mesh（尺度和地面、墙面位置可信）、物理常识（杯子大约 10 厘米高）、物理仿真（放进去跑一下就知道稳不稳）。

合格标准人怎么看机器怎么测参照物
① 能用于仿真导入后看会不会报错、会不会倒拓扑检查：是否封闭（像一个能装水的容器）、有没有自相交、是不是一个整体。格式校验：USD 用 usdchecker 校验，并在 Isaac Sim 中试加载。静置测试：放进物理仿真，1 秒后看位移物理仿真
② 尺寸对和实物比一下大小尺寸检查：与 SLAM 测量值一致，并落在类别常识范围内SLAM、常识
③ 形状对得上叠在一起看偏了多少观测区偏差：在拍到的表面上取很多点，测每个点到 mesh 的距离，取中位数，用物体尺寸的百分比表示，大小物体才能用同一个标准。轮廓重合度：同一角度拍两张剪影，看重叠比例原始高斯
④ 完整没有半边转一圈看有没有缺块洞检查：有没有破洞边界。补全占比：补全区面积占比过高，说明大部分是"猜"的，要重点复核。GPT 看图打分：只作参考结构常识
⑤ 颜色纹理像并排看两张图外观相似度：同一角度分别渲染 mesh 和高斯，比较两张图（LPIPS，模拟人眼感受的图像相似度，0 表示完全一样）原始高斯
⑥ 贴图干净看有没有接缝和乱码接缝检测：UV 接缝两侧的颜色差。文字检查：GPT 检查文字区域有没有乱码常识

一开始指标不要多，有这 10 个左右就够了。以后发现新的问题类型，再加新指标。

第三步：用人工判断来定阈值

  1. 人工标注：选 100 到 200 个物体，覆盖各种类别，由熟悉业务的同事逐个判断"能不能交付"，不能交付的写明原因。这批数据就是黄金集。
  2. 算指标：对这些物体跑出全部指标数值。
  3. 找分界线：对每个指标，把物体按数值排序，看合格和不合格大概从哪里分开。
  4. 有重叠时宁可严一点：见下方说明。
  5. 按类别分别定：椅子、沙发这类难物体的阈值可以和桌子、柜子不同。
观测区偏差（占物体尺寸的百分比）
合格的：   0.1  0.2  0.2  0.3  0.3  0.4  0.4  0.5
不合格的：                              0.6  0.9  1.2  2.5
                                    ↑
                            阈值定在 0.5% 左右

判断会出两种错：漏放是坏数据通过了，客户会看到，伤害口碑；误杀是好数据被拦下，只是多花一点修复成本。因为是卖给客户的数据，漏放的代价远大于误杀，所以阈值要往严的方向定。

  • 谁来标注黄金集？标注 100 到 200 个物体大约需要 1 到 2 人天。
  • 难类别（沙发、植物、透明物体）是否放宽标准，或和客户约定分档交付？
  • 补全占比的上限定多少？超过多少就必须人工复核？

09Agent 修复回路

Agent 像一个资深工程师那样工作：看指标和渲染图，判断是什么问题，从工具库里选修复手段，修完再用同一个门禁验证。改写建模代码是重要手段，但永远在沙箱里执行，结果永远要过门禁。

运行原则

  • 修复预算：每个物体限制修复轮数和 token 上限，超出就转人工，并附上完整的诊断记录。
  • 模板沉淀：GPT 写出的建模代码如果反复成功（比如"四腿方桌"），就整理成参数化模板放进模板库。之后同类物体只需要 GPT 选模板、给初始参数，甚至不调用 GPT，直接由算法拟合参数。这同时提升了稳定性，也大幅降低了 token 成本。
  • 产出分三级：自动通过、修复后通过、人工复核。初期人工比例会比较高，目标是逐步压到 5% 到 10%。

知识包（skill）：只给 GPT 参与的环节用

先区分三个概念：工具是能执行的操作，本质是代码函数；模板是可复用的建模代码；知识包是教模型怎么做、什么时候做的说明、规范和示例，按需加载。

重建、修复、烘焙这些确定性步骤由流水线直接调用工具，不经过 GPT，不需要知识包。GPT 负责的三件事（理解结构、写建模脚本、诊断问题）做得好不好，很大程度上取决于它拿到的"操作手册"，所以这部分需要知识包：

知识包内容作用
Blender 建模规范只能调用建模原语库；单位、坐标轴、命名约定；禁止的操作减少不合规的脚本
结构建模指南按结构类型（椅子、柜子、沙发等）说明怎么拆部件、常见尺寸范围、典型错误，附 2 到 3 个成功示例提高第一次就做对的概率
诊断手册每类门禁失败的表现、原因、优先使用的修复工具让修复回路收敛更快
纹理补全规则什么时候镜像拷贝、什么时候沿用部件材质、文字区域怎么处理避免乱补纹理

知识包放在代码仓库里自己管理，做版本控制，每次修改都要在黄金集上跑回归。gpt-6-astra 支持 OpenAI 的 skills 工具，但自己管理更可控、可测试，换模型时也能直接带走。

稳定性保障

要分开看两件事。质量稳定靠门禁：不管 GPT 这次发挥好不好，不合格的物体都过不了门禁，交付的数据质量始终稳定。产量稳定靠通过率：GPT 发挥不好只会拉低通过率、增加成本，不会让坏数据流出去。提高通过率的手段：

  • 限制接口：GPT 只能调用建模原语库，不能写原生 bpy。接口越小，出错越少。
  • 结构化输出：结构理解的结果必须是固定格式的 JSON，程序先校验，不合格直接重试。
  • 多候选选优：同一个物体出 2 到 3 个方案，用指标挑最好的，不依赖单次结果。
  • 模板沉淀：常见结构做成模板后，同类物体基本不再依赖 GPT 自由发挥。
  • 锁定版本：固定模型快照版本、知识包版本、Blender 版本。任何一项升级，都要先过黄金集回归。

Blender 池的运行与隔离

  • 进程常驻：Blender 进程常驻，避免反复启动。每个任务开始前重置为空场景，每处理几十个任务重启一次进程，防止内存泄漏。
  • 故障隔离：单个任务设超时。Blender 崩溃只影响这一个任务，系统自动换一个进程重试。
  • 脚本静态检查：执行前检查 GPT 写的脚本，只允许导入白名单里的模块（建模原语库、math 等），禁止文件、网络、系统调用。
  • 容器隔离：Blender 的 Python 默认什么都能做，所以执行环境必须断网，文件系统只读，只开放当前任务的临时工作目录，并限制 CPU 和内存。
  • 不操作界面：不让 GPT 通过截图和模拟鼠标键盘操作 Blender 界面。这种方式演示效果好，但量产太慢、结果不稳定，一律用脚本。

13框架选型

结论：Python + Temporal + 自研的轻量 agent 层，通过 OpenAI Responses API 调用 gpt-6-astra，不用 AgentScope 这类 agent 框架当主框架。真正要选的不是语言，而是要不要让 agent 框架掌控整个系统的执行流程。

为什么不让 agent 框架当主框架

  • Agent 只占系统的一部分。几何处理、GPU 计算、质检和编排都是确定性代码。Agent 负责结构理解、写建模代码和修复诊断，每一步都有明确的输入输出和预算上限。
  • 控制流只能有一个主人。Temporal 负责持久化、断点续跑和重试；agent 框架有自己的消息流和状态管理。两者都想决定"下一步做什么"，出问题时很难定位。
  • agent 层本身不复杂。工具注册表、基于 Responses API 的工具调用循环、预算控制、轨迹记录，自己写几百行，每一步都能打日志、能回放、能单测。
  • 生产系统需要稳定。Agent 框架迭代快、大版本改动多，量产期间不希望被框架升级打断。
方案优点缺点结论
Python + 自研轻量 agent 层完全可控，好调试，和 Temporal 无冲突多智能体协作等高级能力要自己做推荐
AgentScope多智能体协作、原型快、国内生态支持好自带控制流，和 Temporal 重叠；版本变化快以后再评估
LangGraph 等图式流程、生态大同样有控制流重叠的问题，抽象层较厚不作为主框架

接入 gpt-6-astra 的注意事项

  • 工具调用必须用 Responses API。官方文档说明，这个模型的工具调用只能走 Responses API，不能走 Chat Completions。
  • 脚本在自己的 Blender 池里执行，不用 OpenAI 托管的代码执行工具。托管的 code_interpreter、hosted_shell 用起来方便，但数据要传到外部，也调用不了我们的 Blender 建模库和观测数据。把我们自己的工具以函数调用或 MCP 的方式提供给 GPT。
  • 企业账号要管理员开启。即使已有 API 权限，gpt-6-astra 默认也是关闭的。

给以后留的口子

  • 工具按 MCP 协议暴露。以后换 AgentScope 或别的框架，工具库原样复用，只换调度层。
  • 模型调用只走模型网关。换模型或供应商时，业务代码不用改。

14方案评审与高可用

可行性结论

方案可行，但有前提。质量稳定由门禁保证：不合格的物体过不了门禁，交付出去的 mesh 和 USD 质量是稳定的。真正不确定的是通过率和成本，也就是"每天能稳定产出多少合格数据、花多少钱"。这取决于几个关键假设，必须在第 2 周用黄金集验证，不能等到量产才发现。

关键假设第 2 周怎么验证不成立时的备选
A. GPT 程序化建模对规则物体足够好桌、柜、椅、杯、花盆的自动通过率加快模板沉淀，提高人工比例；或评估引入外部 3D 生成 API
B. 单物体 GPT 成本在预算内实测每个物体的 token 消耗更多走模板和封口路线，简单任务换便宜型号
C. 可见性估计可靠人工抽查"接触洞 / 隐藏洞"分类的准确率加强 SLAM 接触关系推理；疑难物体转人工
D. 新视角渲染图足够清晰抽查发给 GPT 的渲染图质量收窄虚拟相机范围，只用高分视角
E. API 配额支撑日产量按目标并发做压测多通道接入，申请提高配额
F. Blender 池吞吐足够单节点每小时处理的物体数加节点；把重计算移到 CPU 池

建议第 2 周结束时开一次评审会，逐条判断是否成立，再决定是否按原计划进入试产。

高并发与高可用

架构上能做到。编排层持久化、工作节点无状态、按资源分池水平扩展，都是成熟做法。评审中发现以下几处风险，其中风险 2 和 3 是原方案漏掉或低估的，已补进方案。

风险 1：外部 API 是单点依赖（最大风险）

OpenAI 一旦限流或故障，所有需要 GPT 的步骤都会停下来。

  • 多通道：模型网关同时接入 OpenAI、Azure、AWS Bedrock 上的 gpt-6-astra，一个出问题自动切换。
  • 阶段解耦：不需要 GPT 的阶段（清理、渲染、融合、封口、对称、烘焙）照常运行；需要 GPT 的请求在队列里缓冲，服务恢复后继续，不丢任务。
  • 熔断：错误率过高时暂停调用，避免把预算浪费在失败请求上。

风险 2：数据搬运（原方案漏掉）

场景高斯体积大，如果每个阶段都从对象存储重新下载，网络和存储会先撑不住。对策：同一个物体的连续阶段固定在同一台机器上执行（Temporal 支持把任务派发到指定节点），节点本地缓存，阶段之间只传裁剪后的物体数据。

风险 3：人工复核会成为瓶颈（原方案低估）

每天约 8,300 个物体，即使只有 10% 需要人工复核，也是每天约 830 个。按每个 1 到 2 分钟计算，每天需要 14 到 28 个人时。

  • 提前安排复核人力；
  • 复核台要高效：自动排优先级、多视角预览、一键通过或打回、直接标注问题类型；
  • 复核结果回流，用来调整门禁阈值、充实知识包。

风险 4：基础组件的高可用

组件高可用做法
Temporal多节点集群，或直接使用 Temporal Cloud；后端数据库主备
PostgreSQL主从复制加自动切换，或云上托管数据库
对象存储MinIO 分布式部署，或云上 S3 / OSS
工作节点无状态，部署在 K8s 上。节点故障时任务心跳超时，自动在其他节点重试
Blender 池进程级隔离，崩溃自动重启，任务自动重试
模型网关多副本部署；多通道接入；队列缓冲

风险 5：缺少发布前的质量保护

修改提示词、知识包、模型版本、Blender 版本或门禁阈值，都可能悄悄拉低质量。

  • 每次修改必须先在黄金集上跑回归，指标不下降才能上线；
  • 新版本先用一小部分流量灰度运行，观察通过率和成本，再全量切换。

风险 6：时间

8 周内把完整的高可用体系和量产一起做完非常紧张。建议分两步：

  • 12 月中旬前：优先保证产量和质量，用托管服务降低运维量（托管数据库、对象存储、Temporal Cloud），模型网关先接两个通道；
  • 之后：再补多区域部署、完善灰度发布等。

其他评审意见

  • 可见性估计有不确定性。没有训练相机位姿，"哪些区域被观测过"只能靠高斯覆盖度推算，会影响补全路线的选择。对策：结合 SLAM mesh 判断接触关系，作为第二个信号。
  • 新视角渲染图可能误导 GPT。偏离训练视角太远时，渲染图会模糊或有伪影。对策：给视角打分，只把高质量视角发给 GPT。
  • 实例拆分少了 2D 分割模型。只靠几何信号和 GPT，紧贴在一起的物体可能拆不开。对策：先观察 G1 失败率，必要时转人工处理。
  • 成本估算未经验证。第 2 周实测后要修正，并据此决定 API 预算。

建议明确的服务目标

目标建议值
日产量约 420 个场景 / 天，并能持续维持
外部 API 故障任务不丢失，恢复后自动继续
单节点故障任务在几分钟内自动转移到其他节点
质量所有交付物都通过门禁，并附带质检报告

  • 超时与心跳：每个阶段都有超时，长任务定期上报心跳，节点故障时自动转移
  • 幂等：同一阶段重跑结果一致，重试不会产生重复数据

16团队问题清单

不管团队怎么回答，整体架构、六阶段流水线和几何路线都不会变。答案影响的只是具体组件、产能规划和交付规格。

优先级问题答案影响什么
必须问清内部训练代码是从零自研，还是基于 Inria 官方代码或改版？代码里导入的是 diff_gaussian_rasterization 还是 gsplat？仓库里的 LICENSE 有没有提到 Inria 或 Max Planck？许可证风险。有问题就改用 gsplat 重训或申请授权，只换组件，架构不变
必须问清公司 OpenAI 账号是否已开通 gpt-6-astra（企业账号需管理员开启）？速率限制等级和月度预算是多少？日产量上限和成本上限
必须问清客户合同是否允许把场景渲染图上传到 OpenAI？合规。不允许的话，整个大模型接入方式要重新考虑
必须问清内部有没有 GPU 机器做计算？多少张，什么型号？高斯渲染和深度融合需要 GPU，不涉及部署模型
必须问清一万个场景必须年底一次交齐吗？能否分批交付或按质量分档？排期和产能，不影响技术路线
尽量问清客户对格式（GLB / USD / URDF）、面数上限、纹理分辨率、坐标系有什么要求？只影响导出阶段
尽量问清能否提供两三个遮挡洞的典型失败案例，最好带原始数据？放进黄金集，第 2 周实测要用
尽量问清每个场景平均有多少个物体？产能和成本估算，目前按 20 个计算
尽量问清能安排多少人做人工复核？每天可能有数百个物体需要复核，见第 14 节风险 3
尽量问清团队现用的 Blender 版本？有没有现成的建模或处理脚本？建模原语库需要 4.5 以上版本（Manifold 布尔求解器）；现有脚本可以直接整理进原语库
知道更好SLAM 用的是 RGB-D、激光，还是两者都有？方案会自动评估 SLAM 可信度，知道了参数能调得更准
知道更好分割高斯是用什么方法得到的？估计分割误差大小，也就是"分割洞"有多常见
知道更好上游是否留存了训练照片和相机位姿？有的话纹理质量能明显提升
